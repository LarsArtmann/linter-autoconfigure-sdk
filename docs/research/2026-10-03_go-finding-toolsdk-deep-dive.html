00Summary

linter-autoconfigure-sdk is a thin, deliberate bridge: it converts its own ProviderSpec / BootstrapSpec into a toolsdk.Spec that BuildFlow discovers. It touches 5 of the 10 Spec fields plus RepairerFunc, RepairResult, and DryRunFromContext — and everything it touches, it touches correctly, including the anti-lie RepairResult{Description} contract and the dry-run channel. The audit found one real defect (a nil-context panic in the bootstrap repair path, empirically reproduced against released v0.7.0 and fixed in this working tree by adopting toolsdk.EnsureContext) and a cluster of design gaps concentrated in one place: the bridge does not carry the declarative DAG surface (Trigger, DependsOn, ModuleFanOut, Options, non-config Inputs), so all three live consumers mutate the returned Spec after the fact.

The bottom line The lifecycle core is fully and correctly leveraged; version currency is perfect. The highest-leverage gap is Inputs modeling: the bridge derives Spec.Inputs only from config filenames, so tools that read more (package.json for project detection, go.work/nix/CI pins for version-surface analysis) under-declare their read contract — which quietly weakens BuildFlow's data-flow edges and result-cache invalidation.

◆What's already excellent

Baseline established from the two bridge files and the test suite; consumer behavior verified against oxlint-auto-configure v0.9.1 and go-version-auto-configure (both on SDK v0.7.0).

+
Anti-lie repair contract honored Every repair returns only RepairResult{Description}; counts ride the description string ("wrote .oxlintrc.json (870 rules)"), never a self-reported fix count — exactly what the toolsdk doc prescribes ("fix counts are measured by re-detection"). bootstrap.go:141-148, autoconfigure.go ProviderFromSpec repair adapter.
+
Dry-run channel adopted correctly Bootstrap repair reads toolsdk.DryRunFromContext before writing (bootstrap.go repair path) and the test suite drives it via the canonical toolsdk.WithDryRun (bootstrap_test.go:273), not a hand-rolled context key.
+
Registry boundary respected The SDK never calls Register/All — registration is documented as consumer-side (provider.go files in both consumers do toolsdk.Register(spec)). Correct layering: the SDK produces a plain value, the consumer publishes it.
+
Suggest-only signal is structural Nil ProviderSpec.Repair leaves Spec.Repair nil — the canonical BuildFlow signal — instead of a sentinel error; the legacy ErrNoRepair is deprecated with a removal date. This predates the audit and matches toolsdk's intent precisely.
+
Drift-as-HealthCheck is semantically sound Verified against BuildFlow source: RunHealthChecks failures are warn-only (execution/pipeline.go:88-90) and surface in the workflow summary; a drifted config implies Detect is idle (Detect only fires when the config is missing), so the advisory channel never masks a real finding.
+
Version currency perfect go.mod pins toolsdk v1.14.0, released 2026-10-01 — two days old at audit time. The v1.13→v1.14 floor bump landed in this working tree's go.mod (unreleased; rides the next tag).

01Findings

Ordered by impact. Evidence cites SDK code, toolsdk source/docs, consumer code, and BuildFlow internals.

Anti-pattern · Fixed during this audit

Nil-context panic: EnsureContext existed for exactly this and was never used

bootstrap.go:219 (pre-fix) · reproduced against released v0.7.0

toolsdk.DryRunFromContext(ctx) dereferences ctx (ctx.Value on a nil interface panics). The SDK's own WorkingDir has been nil-safe since the v0.4.1 hotfix — same bug class — but the bootstrap repair closure called DryRunFromContext before any guard. A standalone caller passing nil ctx (legal per the SDK's "closures usable standalone" contract) crashed. toolsdk ships EnsureContext precisely for Detect/Repair implementations; the SDK ignored it. 

// Reproduced against v0.7.0 (clean module, toolsdk v1.13.0):
provider.Repair.Repair(nil)
// panic: nil pointer dereference
//   toolsdk.DryRunFromContext  dryrun.go:17
//   BootstrapSpec.repair       bootstrap.go:219

// Fix applied in this working tree (all five derived entry points):
Repair: toolsdk.RepairerFunc(func(ctx context.Context) (toolsdk.RepairResult, error) {
    description, err := spec.repair(toolsdk.EnsureContext(ctx))  // was: spec.repair(ctx)
    ...
})
Fix: shipped in this working tree All five derived capabilities (both Detect adapters, both repair closures, the drift HealthCheck) now normalize with toolsdk.EnsureContext before running, so consumer closures never observe a nil ctx. Regression tests added: TestBootstrapNilContext, TestProviderFromSpec_NilContext_NormalizedBeforeClosures. golangci step green, full race suite green.
Partially used · Data-flow correctness

Inputs derive only from config filenames — tools that read more must under-declare

autoconfigure.go discoveryCandidateStrings · oxlint-auto-configure/pkg/provider/provider.go:119 · go-version-auto-configure/pkg/provider/provider.go:40-46

toolsdk doc: Inputs are "the file patterns this tool reads. Used to derive data-flow edges and to gate the tool on file presence." The bridge derives Inputs exclusively from ConfigFiles — there is no field for anything else a tool reads. oxlint-auto-configure works around it by prepending to bridge-derived state: spec.Inputs = append([]string{"package.json"}, spec.Inputs...) (provider.go:119). go-version-auto-configure does not work around it: its spec declares ConfigFile go.mod only, yet surface.Discover also reads go.work, .github/workflows, and nix pins — none of which are Inputs, so edits there cannot invalidate this tool's cached results in BuildFlow's result cache. 

// Today (consumer reaches into bridge-derived state):
spec.Inputs = append([]string{"package.json"}, spec.Inputs...)

// Target (bridge owns the full read contract):
type BootstrapSpec[T any] struct {
    ...
    // ExtraInputs lists non-config read patterns (prepended to
    // the derived Inputs, e.g. "package.json").
    ExtraInputs []string
}
Recommendation Add an ExtraInputs []string field to both spec types; the bridge prepends them to the derived candidates. Additive, zero breakage, removes the only sanctioned reason to mutate the returned Spec. Then fix go-version-auto-configure to declare its full read surface (go.work, workflows, nix pins).
Partially used · Declaration locality

Trigger, DependsOn, ModuleFanOut have no bridge fields — 2/2 live consumers mutate post-hoc

oxlint provider.go:106-114 · go-version provider.go:51 · toolsdk Spec docs · BuildFlow sdk_registry.go ToolFromSpec

BuildFlow's ToolFromSpec converts every Spec field — Trigger to file-contract triggers, DependsOn to DAG policy, ModuleFanOut to per-module topology. The bridge zeroes all three and its docs bless post-hoc mutation ("set them on the returned Spec when needed"). Both consumers do exactly that: oxlint sets a 9-pattern JS Trigger and an empty DependsOn with a four-line comment explaining a DAG-flip decision; go-version sets OnFiles("go", "go.mod", "go.work"). The mutation is legal (plain value) but it splits one tool's declaration across two files, and toolsdk's own changelog warns the parity fields are easy to lose ("a spec that omits the field silently loses per-module fan-out at conversion time").

Recommendation Add optional Trigger toolsdk.Trigger and DependsOn []string (and ModuleFanOut bool for completeness) pass-through fields to both spec types. Zero when unset — identical behavior — but the whole tool declaration lives in one struct literal. Cheap API growth now, before v1 freezes it out.
Partially used · Bridge asymmetry

ProviderSpec cannot declare a HealthCheck; BootstrapSpec can

autoconfigure.go ProviderSpec fields · go-version provider.go:52

The bootstrap bridge derives a HealthCheck (the drift advisor); ProviderSpec has no HealthCheck field at all, so go-version-auto-configure bolts one on after conversion: spec.HealthCheck = fix.SelfCheck (provider.go:52) — a real external-dependency check (the exact use case toolsdk documents) forced through post-hoc mutation.

Recommendation Add HealthCheck func(ctx context.Context) error to ProviderSpec (nil = none, matching toolsdk). Restores symmetry between the two bridges with one additive field.
Missed opportunity · Low urgency

v1.14.0 Options not bridged — oxlint profiles are the natural first knob

toolsdk v1.14.0 CHANGELOG · not used anywhere in the SDK

toolsdk v1.14.0 added declarative per-run knobs (Spec.Options, WithOptions, OptionsFromContext, ValidateOptions). Neither bridge type carries Options. oxlint-auto-configure already has the shape of a knob — "custom profiles remain a CLI concern" (provider.go comment) — a profile: strict | recommended | ... option would let BuildFlow runs tune it without the CLI. But no consumer has asked, and the SDK's v1 freeze is approaching: adding pass-through Options []toolsdk.Option is a one-line field when demand materializes. Defer.

Nice to have · Standing decision reaffirmed

errConfigDrift stays unexported — still no consumer demand

bootstrap.go errConfigDrift · owner decision 2026-09-22

Consumers cannot errors.Is-match the drift sentinel; both current consumers surface the error text without branching on it. Searched both consumer repos: no sentinel or string matching anywhere. The export-on-demand decision stands; revisit when a consumer needs programmatic drift branching.

Consumer debt surfaced by the audit

go-version-auto-configure hand-rolls a nil-unsafe copy of the SDK's exported WorkingDir

go-version provider.go:135-144 vs autoconfigure.WorkingDir

The SDK exports WorkingDir(ctx) precisely so Analyze/Repair closures stop hand-rolling the fallback ("instead of hand-rolling the fallback", its doc comment). go-version-auto-configure duplicates it verbatim — and its copy omits the nil-ctx guard, so a nil ctx panics there too. Consumer-side fix: delete the local helper, call autoconfigure.WorkingDir(ctx). Noted here because the SDK's discoverability (README example for closure authors) could have prevented it.

02What the solution could look like

The target bridge: same lifecycle core, plus pass-through fields so a tool's entire BuildFlow declaration is one struct literal. Additive only — every field zero-value preserves today's behavior exactly. 

type ProviderSpec struct {
    Name, Description, ConfigFile, ConfigFiles  // unchanged
    Analyze func(context.Context) ([]ConfigIssue, error)
    Repair  func(context.Context) (string, error)

    // New, all optional, forwarded verbatim to toolsdk.Spec:
    Trigger      toolsdk.Trigger   // zero = unset, consumer may still set
    DependsOn    []string
    ModuleFanOut bool
    ExtraInputs  []string       // prepended to derived Inputs
    HealthCheck  func(context.Context) error
}

// BootstrapSpec[T] gains the same five pass-through fields;
// its drift HealthCheck stays unless overridden.
This is the target Post-hoc mutation remains legal for exotic cases, but the three live consumers' mutations all collapse into spec literals — and the Inputs under-declaration in go-version-auto-configure becomes expressible (and lintable) in one place.
