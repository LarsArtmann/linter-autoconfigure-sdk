00Verdict

The architecture and data model are not superb. They rest on a correct idea — extract the plumbing two auto-configurers duplicate — and several individual decisions are good. But the package as committed does not compile in its own documented environment, and the data model mixes three different typing policies inside a single 6-field struct while a flagship helper silently fabricates line numbers and swallows errors.

The bottom line. One fatal issue (broken build from a dependency the project's own AGENTS.md forbids) plus a cluster of type-safety gaps on the core types. Fix the dependency pin first — nothing else can be verified until the package builds. Then unify the typing policy and make FindingFromIssue honest. Everything else is polish.

This is an early-stage library with zero consumers, so the cost of fixing everything is low and the cost of leaving it is that the first real consumer inherits a broken, inconsistent foundation. The right time to harden the model is now, before golangci-lint-auto-configure or oxlint-auto-configure depends on it.

◆What is already excellent

Before the criticism: these decisions are sound and should be preserved through any refactor.

+
Correct extraction instinct Config round-trip + finding emission + provider shape is exactly the plumbing that does not belong in each tool. The "why" is right; only the "how"> is broken.
+
ConfigError mirrors os.PathError The {Op, Path, Err} shape is a familiar, well-understood error contract. Callers already know how to read it.
+
Error-chain traversal is tested errors.Is(err, fs.ErrNotExist) and errors.As(err, &json.SyntaxError{}) both work through *ConfigError. The contract is proven, not assumed.
+
Generic LoadJSON[T] Idiomatic Go generics; one helper instead of per-config-type loaders.
+
Refuses false convergence No shared YAML library (tools use incompatible libs) and no shared ProjectType enum (Go shape vs JS framework). Both omissions are deliberate and correct — forcing either would couple tools that should stay independent.
+
Honest self-assessment in the README "The weakest of the 5 SDKs — value over stdlib is modest until a second auto-configurer lands." That honesty is a strength. Keep it.

01Critical findings

Blockers. The package cannot ship until these are resolved.

Blocking · Fatal

The SDK does not compile

go.mod: go-finding v1.3.0 · autoconfigure.go:27 import

go build ./..., go vet ./..., and go test ./... all fail. go-finding v1.3.0 transitively imports encoding/json/v2 and encoding/json/jsontext, both excluded by build constraints in this NixOS toolchain. The package's only non-stdlib dependency — the one that gives it a reason to exist (finding.Finding) — cannot be imported. The SDK is, today, dead code. 

$ go build ./...

BUILD_EXIT=1   VET_EXIT=1   go test: [setup failed]
Fix. Revert the dependency to v1.1.x. The project's own AGENTS.md already says "Do NOT upgrade to go-finding v1.2+. v1.2.0 switched to encoding/json/v2 ... The entire package fails to compile." — and then go.mod moved to v1.3.0 anyway. go get github.com/larsartmann/go-finding@v1.1.x, confirm go build ./... is green, and gate the version in CI.
Blocking · Source-of-truth split brain

Three files disagree about the dependency version

go.mod vs README.md:35 vs AGENTS.md

One fact, three claims:

02Data model findings

The data model is four types: ConfigError, ConfigIssue, ProviderSpec, and the ErrNoRepair sentinel. Each has at least one flaw a strong type system would have prevented.

High · Type safety

Inconsistent coupling to go-finding's branded types

autoconfigure.go:118-136 (ConfigIssue) · :141 (FindingFromIssue)

Inside one 6-field struct, three string-ish fields use three different typing policies:

Field Type used go-finding offers
ConfigIssue.Severity finding.Severity (typed) —
ConfigIssue.File raw string finding.FilePath
ConfigIssue.Rule raw string finding.RuleName
FindingFromIssue(toolName …) raw string finding.ToolName

The README justifies the raw File as "keeps the SDK decoupled from finding's branded types." That justification is false: the package is already fully coupled — it imports finding.Severity, finding.Finding, finding.Builder, finding.Pos, finding.CategoryConfiguration, and finding.FixStrategySuggest. Decoupling one field while coupling six others is not a boundary; it is an arbitrary gap that forces consumers to convert at the call site for zero benefit.

Current — mixed policy
Consistent — adopt the brands
type ConfigIssue struct {
    Rule       string            // raw
    Message    string
    Severity   finding.Severity  // typed
    File       string            // raw
    Line       int
    Suggestion string
}
type ConfigIssue struct {
    Rule       finding.RuleName
    Message    string
    Severity   finding.Severity
    File       finding.FilePath
    Line       int
    Suggestion string
}
// toolName becomes finding.ToolName too
Decision. Either adopt the branded types everywhere (preferred — the coupling already exists, so take the safety it buys) or reject them everywhere and wrap at a single boundary. The current half-and-half is the worst of both options.
High · Stringly-typed

ConfigError.Op is a stringly-typed operation

autoconfigure.go:42-49

Op string carries an informal prose vocabulary ("read" / "unmarshal" / "marshal" / "mkdir" / "write") with no compile-time guarantees. Typos like "wrtie" are silently legal. A consumer's switch ce.Op cannot be exhaustiveness-checked. This is the textbook P1 anti-pattern, and it sits on the package's flagship error type. 

// Closed, exhaustive, typo-proof:
type Op string

const (
    OpRead      Op = "read"
    OpUnmarshal Op = "unmarshal"
    OpMarshal   Op = "marshal"
    OpMkdir     Op = "mkdir"
    OpWrite     Op = "write"
)
High · Dishonest output

FindingFromIssue fabricates line numbers and swallows errors

autoconfigure.go:141-166

Two related defects in the package's most important conversion function:

1. Invented positions. ConfigIssue.Line is documented as "0 if unknown," but FindingFromIssue silently rewrites line <= 0 to 1. The emitted finding then points at line 1 — a specific, authoritative-looking location that is very probably wrong. go-finding ships finding.FilePos(file) precisely for line-less, file-level findings; the SDK ignores it and lies instead.

2. Silent failure. When builder.Build() returns an error, FindingFromIssue discards it and returns finding.Finding{} (the zero value). A caller iterating a slice of issues receives valid findings interleaved with an invisible invalid one, with no signal that a finding was dropped. go-finding even provides MustBuild() for the "inputs are caller-controlled, failure is a programmer error" case — the SDK picks the third, worst option.

Current — silent + dishonest
Honest
func FindingFromIssue(tool string, issue ConfigIssue) finding.Finding {
    line := issue.Line
    if line <= 0 { line = 1 }       // lie
    ...
    f, err := builder.Build()
    if err != nil {
        return finding.Finding{}     // swallow
    }
    return f
}
func FindingFromIssue(tool finding.ToolName, issue ConfigIssue) (finding.Finding, error) {
    pos := finding.Pos(issue.File, issue.Line, 1)
    if issue.Line == 0 {
        pos = finding.FilePos(issue.File) // honest
    }
    ...
    return builder.Build()   // propagate
}
Note on the signature change. Returning (Finding, error) is a breaking change. There are zero consumers today, so the cost is zero. After the first consumer lands, this becomes expensive — another reason to fix it now.
High · Reintroduced split brain

Fix-strategy zero value reopens a bug go-finding deliberately fixed

autoconfigure.go:155-158

When Suggestion == "", the SDK never sets a fix strategy, leaving FixStrategy at its zero value "". go-finding's own NormalizeFixStrategy exists because "" and FixStrategyNone both meant "no fix" but compared unequal — a split brain the upstream package explicitly killed. This SDK reintroduces it at the boundary. Call finding.NormalizeFixStrategy or explicitly set FixStrategyNone.

Medium · Mutability

ConfigError fields are exported and mutable

autoconfigure.go:42-49

Op, Path, and Err are all exported, inviting post-construction mutation of an error value after it has been observed and possibly cached by a caller. Errors should be immutable after creation. Export the values via methods (Op(), Path(), Unwrap()) or keep the fields exported but document immutability — and stop short of returning *ConfigError aliases that callers can mutate.

03Architecture findings

High · Speculative abstraction

Extracted before the second consumer existed

README.md:149 ("No active consumers yet")

The README's own words: "value over stdlib is modest until a second auto-configurer lands." There are zero consumers. Shared plumbing should be extracted when duplication is proven by two callers — not pre-emptively modeled from one. The ProviderSpec shape, in particular, is designed against an imagined consumer and carries no behavior to validate the design. Build the second auto-configurer first; let the real duplication tell you what this SDK's surface should be.

Not "delete the SDK." The config round-trip + typed-error helpers are modest but legitimate. The point is the shape — especially ProviderSpec — should be derived from a real second consumer, not asserted ahead of time. Mark the package v0 / experimental until that consumer exists.
Medium · No behavior

ProviderSpec is a struct of function pointers with no methods

autoconfigure.go:184-194

It carries Analyze and Repair closures returning bare error — a different error policy from the typed *ConfigError helpers sitting next to it, in the package whose entire purpose is a typed-error discipline. There is no ProviderFromSpec(spec) adapter (promised in the README, never started), no validation, and zero in-repo consumers (grep confirms). Either build the adapter and prove the shape, or remove the type until a consumer forces its design.

Low · Dead public API

ErrNoRepair is exported, untested, and unused

autoconfigure.go:196-198

A package-wide exported sentinel with no test, no example, and no reference anywhere in the codebase (confirmed by repo-wide grep — only its own definition and the README table mention it). It is a public contract nobody holds. Either wire it into ProviderSpec (e.g. a nil Repair returns ErrNoRepair from the adapter) or remove it.

Low · Questionable surface

ReadConfig is now os.ReadFile + a one-line wrap

autoconfigure.go:69-76

After the typed-error refactor, ReadConfig's entire value over stdlib is the *ConfigError. A smaller, more composable surface would be func WrapError(op Op, path string, err error) *ConfigError, letting consumers call os.ReadFile directly and wrap at the boundary. Worth deciding before the first consumer locks the shape in.

Low · Footgun

SaveJSON can corrupt a user's linter config

autoconfigure.go:96-111

It hardcodes 0o644 and uses json.Marshal (compact) for configs that are typically human-edited, and it writes in place with no temp-file + rename. A partial write or a crash mid-write leaves the user's linter config truncated. Linter configs are files people edit by hand and depend on for every build — corrupting one is a bad-faith outcome. Use atomic write (write temp in same dir, os.Rename) and accept an indent option.

04What "superb" would look like

The target state. Small package, honest types, one error policy, and a proven shape. 

// One error policy across the whole package.
type Op string // read | unmarshal | marshal | mkdir | write

const (
    OpRead Op = "read"; OpUnmarshal Op = "unmarshal"; OpMarshal Op = "marshal"
    OpMkdir Op = "mkdir"; OpWrite Op = "write"
)

type ConfigError struct {
    op   Op
    path string
    err  error // never nil
}
func (e *ConfigError) Error() string { ... }
func (e *ConfigError) Unwrap() error { return e.err } // idiomatic; fix the linter, not the type

// Branded types used consistently — the coupling already exists, so take the safety.
type ConfigIssue struct {
    Rule       finding.RuleName
    Message    string
    Severity   finding.Severity
    File       finding.FilePath
    Line       int            // 0 => file-level finding
    Suggestion string
}

// Honest conversion: no fabricated lines, no swallowed errors.
func FindingFromIssue(tool finding.ToolName, issue ConfigIssue) (finding.Finding, error) {
    pos := finding.Pos(issue.File, issue.Line, 1)
    if issue.Line == 0 { pos = finding.FilePos(issue.File) }
    b := finding.NewBuilder(issue.Rule, tool, issue.Message, issue.Severity, pos).
        WithCategory(finding.CategoryConfiguration)
    if issue.Suggestion != "" {
        b = b.WithFixStrategy(finding.FixStrategySuggest).WithSuggestion(issue.Suggestion)
    } else {
        b = b.WithFixStrategy(finding.FixStrategyNone)
    }
    return b.Build()
}
Why this is better. One error policy (typed Op, real Unwrap). One typing policy (branded types everywhere they exist). Honest positions and errors. No dead API. The surface is smaller and every type earns its place.

05Recovery roadmap

Ordered so each step unblocks verification of the next.

1

Make it compile

go get github.com/larsartmann/go-finding@v1.1.x. Confirm go build ./..., go vet ./..., and go test ./... are green. This is the only step that matters until it is done — nothing else can be trusted while the package is dead code.

2

Kill the version split brain

Reconcile go.mod, README, and AGENTS.md to one claim. go.mod is the fact; AGENTS.md carries the "do not exceed v1.1.x, here is why" constraint. README links to AGENTS.md instead of restating a version. Add a CI gate (go mod tidy + build) so a bump can't silently land again.

3

Unify the data model

Adopt branded types consistently (or reject consistently). Make Op a typed enum with constants. Restore Unwrap() error and fix the linter/false-positive upstream rather than redesigning the type around it.

4

Make FindingFromIssue honest

Return (Finding, error). Use finding.FilePos for line-less issues. Normalize the fix strategy. Add a test for the builder-error path (previously uncovered, the cause of the 88.9% coverage gap).

5

Atomic SaveJSON + indent option

Temp-file + os.Rename so a crash can't truncate a user's config. Accept an indent option (or default to 2-space) since these files are hand-edited.

6

Prove or cut ProviderSpec

Either build ProviderFromSpec and wire one real consumer (the README's own success criterion), or remove ProviderSpec + ErrNoRepair until a consumer forces the design. Mark the package experimental until then.
